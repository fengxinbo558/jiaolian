# 实时健身教练完整体验设计

**日期：** 2026-08-19  
**状态：** 已经用户确认体验方向，待进入实施计划  
**范围：** 徒手深蹲、开合跳、动作素材库、实时语音纠正、单组总结与训练结束流程

## 1. 背景

当前产品已能检测用户动作、计数和输出一些纠正，但核心体验仍有三类问题：

1. 检测和语音反应慢，用户已进入下一阶段时仍听到旧提示。
2. 快速连续动作中语音过长、过多，教练会打乱用户节奏。
3. 产品只关注单帧或单次动作，缺少从选择动作到结束训练的完整闭环。

本设计的核心不是增加播报数量，而是让每条信息在正确时间出现，并在失去行动价值时立即失效。

## 2. 产品目标

### 2.1 主要目标

- 用户按自然节奏开始和完成动作，无需等待语音指令。
- 画面提示跟随当前动作阶段，过期提示不再显示或播放。
- 训练中只使用短、当前、可执行的微口令。
- 单次动作和整组训练都有明确的反馈和下一步建议。
- 不确定时少说，不把跟踪失败误报成姿势错误。
- 训练结束后立即停止推理和摄像头占用。

### 2.2 非目标

- 不使用 2D 摄像头宣称测量真实肌肉受力。
- 不把低分辨率 GIF 逐帧差异当作动作对错的直接判据。
- 不在连续训练中播放完整长评价。
- 不在默认模式下强迫用户按固定节拍运动。

## 3. 核心体验原则

1. **跟随用户，不指挥用户等待。**
2. **过期信息宁可不说，也不能补播。**
3. **语音不等于全部信息。** 实时语音只承担必须立即知道的内容；其余内容由画面卡片和总结承担。
4. **一次只纠正一件事。** 按安全性、影响程度和可执行性选出最重要问题。
5. **错误判断必须有置信度。** 低置信度只能导致暂停判断，不能导致姿势负评。
6. **评价必须可行动。** 每条负反馈都包含“刚才发生了什么”和“下一次怎么做”。

## 4. 完整用户旅程

### 4.1 选择动作

用户从动作库选择深蹲、开合跳或其他动作。动作详情页显示：

- 动作名称、器械、目标肌群和辅助肌群。
- 授权允许时显示参考 GIF 或自有演示视频。
- 三个最重要的动作要点。
- 推荐拍摄角度、需要的场地空间和安全提醒。

开合跳默认使用正面视角；深蹲允许正面或侧面，并告知两种视角可检查的问题不同。

### 4.2 入镜与校准

训练开始前进入 `FRAMING` 状态。界面必须区分：

- 未检测到人体。
- 身体被画面边缘裁切。
- 动作所需的关键点暂时不稳定。
- 拍摄角度不利于当前动作。

只有在连续稳定可见且用户处于安全起始位时，系统才进入 `READY`。校准保存身体比例、站距、自然站立角度和当前视角，用于个人化阈值，不使用单一绝对坐标。

### 4.3 准备与自由开始

`READY` 状态只说一次“可以开始”。默认不倒计时，不要求用户等待语音。训练前可用一句话说明呼吸原则，训练中呼吸不抢占姿势纠正。

### 4.4 训练中

每帧分析产生结构化状态，不直接产生一长串中文。状态机进入 `ACTIVE_REP` 后：

- 画面提示可以每帧跟随动作阶段。
- 语音只使用 300–600 毫秒的微口令，例如“挺胸”、“手举高”、“脚打开”。
- 同一次动作最多语音提醒一个问题。
- 非安全问题需要连续证据；单帧异常只记录。
- 合格动作使用轻提示音或视觉计数，不播放完整句子。
- 安全风险可以用“停一下”中断其他音频。

### 4.5 单次动作结束

完成一次动作后，分析器输出结构化结果：动作编号、是否合格、主要问题、次要问题、动作时长和置信度。

- 上一动作卡片立即更新，并保留到下一次结果。
- 如果用户未进入下一次动作，可播放一条微口令。
- 如果用户已开始下一次，则不播放上一次的语音评价。
- 快速动作的纠正必须使用“下一次……”的语义，不假装仍能改变已完成的当前动作。

### 4.6 暂歇、遮挡与恢复

状态机区分 `RESTING`、`TRACKING_LOST` 和 `SESSION_ENDING`。

- 开合跳停止 1.5–2 秒后可进入 `RESTING`，但不自动总结。
- 深蹲允许 3–5 秒站立休息，不把站立误判为训练结束。
- 遮挡期间冻结未完成动作的转移；持续丢失后丢弃该次动作，不补算。
- 恢复后要求连续稳定可见并回到安全起始位，然后才重新武装计数。
- 暂歇中只显示状态，不反复播报“请继续”。

### 4.7 训练结束

完整总结优先由用户点击“结束训练”触发。长时间不动只显示“还要继续吗”，不擅自结束。

进入 `SESSION_ENDED` 后：

1. 停止帧捕获和姿势推理。
2. 停止所有未完成语音任务。
3. 关闭摄像头轨道并明确显示已关闭。
4. 生成一份可执行的整组总结。

总结只保留三个核心层级：

- 完成次数和合格次数。
- 本组最常见的一个问题。
- 下一组唯一重点。

例如：“完成 12 次，合格 9 次。最常见问题是身体前倾 3 次。下一组只要注意抬起胸口，保持背部稳定。”

总结页明确显示“摄像头已关闭”，并提供“再练一组”、“查看标准动作”、“选择其他动作”和“返回动作库”。只有用户选择重新训练时才再次请求摄像头。

## 5. 反馈时效模型

每个反馈事件必须包含：

```ts
interface CoachEvent {
  id: string;
  exerciseId: string;
  sessionId: string;
  repId?: number;
  phase?: string;
  kind: "safety" | "tracking" | "correction" | "phase" | "result" | "encouragement";
  priority: number;
  createdAt: number;
  expiresAt: number;
  visualMessage: string;
  speechMessage?: string;
  speechMode: "none" | "micro" | "summary";
  scope: "current-phase" | "current-rep" | "next-rep" | "session";
  confidence: number;
}
```

调度器在显示或播放前重新验证：

1. 当前会话、动作、次数和阶段是否与事件一致。
2. 当前时间是否已超过 `expiresAt`。
3. 置信度是否达到该动作和问题的阈值。
4. 新的高优先级事件是否已替代它。
5. 预计剩余阶段时间是否足以播完语音。

任何一项不满足都丢弃语音，不进入补播队列。

语音优先级：

`safety > tracking > correction > phase > result > encouragement`

同一错误在连续动作中需要重复证据后才首次播放，播放后进入冷却窗口。问题明显恶化或变为安全风险时可以突破冷却。

## 6. 语音播放与中断体验

### 6.1 微口令

训练中只使用完整、不可再拆分的短句。每条微口令在目标语速下应在 600 毫秒内播放完成。

微口令不含“刚才这一次……”等前缀，历史归属由画面卡片承担。

### 6.2 中断规则

- 安全事件可以立即中断任何音频。
- 阶段切换不启动新的长语音，因为训练中不存在长语音。
- 用户在微口令播放中开始下一次时，如果该口令仍对下一次有效，可以播完；否则停止。
- 如底层音频能力支持，停止时使用 80–120 毫秒淡出；不支持时必须通过微口令长度避免产生难以理解的半句。
- 总结播放中用户重新开始训练时，在当前短语边界停止剩余总结，不继续补播。

## 7. 时延与节奏目标

### 7.1 系统时延

- 新视频帧应在到达后立即进入单帧在线分析，忙时丢弃旧帧，不积压队列。
- 目标视觉阶段反馈延迟低于 150 毫秒。
- 目标微口令开始延迟低于 250 毫秒。
- 超过延迟预算的事件只更新画面或记录，不再播放。
- 推理、分析、调度和语音开始时间分别记录，验收时使用 P50/P95 而不是单次最好值。

### 7.2 深蹲节奏

没有适用所有训练目标的唯一标准速度。对本产品的默认徒手深蹲模式，使用以下产品验收区间，而不是强制节拍：

- 完整一次默认可接受约 1.2–3.0 秒。
- 主要自然区间约 1.5–2.5 秒。
- 下蹲约 0.7–1.3 秒，底部不强制停留，起身约 0.6–1.2 秒。
- 只有达到明显失控的个人化快速阈值才提示“下蹲慢一点”。
- 不要求用户为等待呼吸或纠正语音而延长动作。

## 8. 动作分析规则

### 8.1 深蹲

阶段：`READY -> DESCENDING -> BOTTOM/REVERSAL -> ASCENDING -> LOCKOUT -> READY`。

主要问题：

- 深度不足。
- 身体前倾，仅在支持的视角和置信度下判断。
- 正面视角下的膤盖内移趋势，必须基于个人站立基线，不使用一个绝对宽度比例评判所有人。
- 下蹲失控过快。
- 未完整回到站立锁定位。

计数和合格必须分开：完整下蹲并回到站立可计为完成一次，即使存在深度问题；“合格”由该次动作的问题记录决定。

### 8.2 开合跳

阶段：`CLOSED -> OPENING -> OPEN -> CLOSING -> CLOSED`。只有完成一个闭环才计数。

主要问题：

- 手腕未达到头部或规则要求的高度。
- 脚间距未达到基于髋宽和个人基线的打开幅度。
- 手脚时序明显不同步。
- 左右幅度明显不对称。
- 未回到完整闭合位。
- 躯干明显偏斜或失去稳定。

张开最大幅度用于评估手臂和脚距；返回闭合位用于确认一次计数。普通 2D 摄像头不可靠地测量真实地面冲击力，因此只能就可见的落地稳定性进行保守提示，不宣称测得关节受力。

## 9. 素材库集成

`hasaneyldrm/exercises-dataset` 用于以下用途：

- 动作目录、动作别名、分类、器械和肌群信息。
- 经人工润色的中文步骤说明。
- 在媒体授权允许时的训练前演示。
- 训练结束后的标准动作复习入口。

它不直接提供姿势判定阈值。产品内部建立独立的 `ExerciseCoachProfile`：

```ts
interface ExerciseCoachProfile {
  exerciseId: string;
  catalogSourceId?: string;
  supportedViews: string[];
  requiredLandmarks: number[];
  phases: PhaseDefinition[];
  formRules: FormRule[];
  microCues: Record<string, string>;
  preparationCues: string[];
  summaryAdvice: Record<string, string>;
  mediaAttribution?: string;
  mediaLicenseStatus: "metadata-only" | "development-reference" | "licensed" | "owned";
}
```

开合跳对应数据集的 `3224 jack jump (male)`。数据集字段和指导文字可依 MIT 条款集成并保留许可说明；图片和 GIF 属于 Gym Visual，未获得适用产品的独立授权前不作为正式商用资产打包发布。

## 10. 界面信息层级

训练页始终区分三个区域：

1. **当前提示：** 仅显示当前阶段和当前可执行纠正，不保留历史。
2. **上一动作：** 明确标注第几次、是否合格、主要问题和下一次建议。
3. **本组进度：** 完成次数、合格次数和当前训练状态。

实时提示不得覆盖视频中的脚踝、手腕等关键检测区域。语音合成与读屏直播区不同时重复播放相同内容。

## 11. 隐私与资源生命周期

- 姿势推理默认在本机完成。
- 默认不保存原始视频或单帧图像。
- 历史记录默认只保存动作、次数、时长和问题统计。
- 用户结束训练、摄像头轨道中断、页面卸载或切换训练会话时，都必须正确停止帧捕获和 Worker 分析。
- 页面隐藏时停止发送新帧；恢复可见后重新确认人体和起始位。

## 12. 失败处理

- 模型加载失败：告知用户不能开始分析，提供重试，不显示虚假的“已准备”。
- 摄像头被撤销或中断：立即暂停训练状态，清理旧帧，提供重新开启入口。
- 推理持续超时：自动降低捕获频率或输入分辨率，但不积压旧帧；无法维持最低实时性时明确暂停语音纠正。
- 姿势跟踪丢失：使用中性识别文案，不猜测用户需要后退或姿势错误。
- 统计为零：总结显示“尚未完成完整动作”和明确的重试步骤，不显示“暂无明显问题”。

## 13. 测试与验收

### 13.1 状态机测试

- 深蹲在 15/30/60 FPS 重采样下计数、合格结果和事件顺序一致。
- 开合跳在 0.5–1.2 秒单次节奏下只按 `CLOSED -> OPEN -> CLOSED` 计数。
- 底部或最大张开位的小幅抖动不得重复计数。
- 中途遮挡不得补算未完成动作。
- 启动时位于动作中间位不得补算。
- 暂歇和恢复不清空已完成次数。

### 13.2 过期信息测试

- 用户进入起身后，“继续下蹲”永远不得启动。
- 用户进入下一次开合跳后，上一次的完整评价不得播放。
- 任何过期事件不得在之后空闲时补播。
- 安全事件可以中断当前提示，非安全的低优先级事件不得中断正在生效的姿势纠正。
- 总结期间重新运动时，剩余总结不再播放。

### 13.3 语音体验测试

- 每条训练中微口令的实际播放时长达标。
- 没有播放到一半无法理解的长句。
- 语音开启时同一文案不被读屏和 TTS 重复朗读。
- 关闭语音后所有核心信息仍可从画面获得。
- 快速连续动作中没有语音队列增长。

### 13.4 性能验收

- 使用实际摄像头、CPU 和典型光线环境记录端到端 P50/P95。
- 高负载时帧会被丢弃而不是排队，延迟不随训练时间持续增长。
- 低性能设备上的降级模式不改变计数语义。
- 在发布前使用不同身高、体型、衣着和拍摄角度的真人试用进行回归。

### 13.5 完整旅程验收

至少覆盖以下端到端场景：

1. 首次授权、查看演示、入镜、完成一组深蹲、结束并关闭摄像头。
2. 开合跳快速连续动作，中途出现一种持续错误，暂歇后查看建议。
3. 训练中遮挡、恢复、继续完成和正常总结。
4. 训练中摄像头轨道中断，用户重新开启后继续。
5. 用户在总结播放中立即开始新一组，旧总结正确停止。

## 14. 实施优先级

### P0：必须先解决

- 找回或恢复原健身项目源码，并建立可重复启动和验证的工作区。
- 反馈事件有效期和过期丢弃。
- 语音不排队，微口令化，安全优先级。
- 帧捕获单帧在线，忙时丢帧。
- 训练结束后停止推理和摄像头。
- 开合跳的独立状态机、计数和最小纠正集。

### P1：完成体验闭环

- 动作素材目录和演示页。
- 按动作区分的拍摄角度和校准。
- 上一动作卡片、暂歇状态和整组总结。
- 结构化延迟遥测和真机性能验收。

### P2：扩展能力

- 更多动作的 `ExerciseCoachProfile`。
- 自有标准视频和多体型、多视角参考序列。
- 移动端音频、触感反馈和性能优化。

## 15. 完成定义

仅在以下条件全部满足时，本轮实时教练体验改造才算完成：

- 用户无需等待口令即可以自然开始深蹲和开合跳。
- 快速连续动作中不会听到已过期的阶段指令。
- 不存在语音排队导致的延迟累积。
- 每个负反馈都能在画面上对应到具体动作编号，并给出下一次可执行建议。
- 跟踪不稳定时不会自信地生成姿势负评。
- 暂歇、遮挡、恢复、结束和重新开始都有明确且不冲突的状态。
- 用户结束后摄像头确实关闭，并得到简洁、具体、可执行的总结。
