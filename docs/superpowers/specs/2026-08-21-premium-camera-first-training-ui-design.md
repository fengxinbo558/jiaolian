# 高级相机优先训练体验设计

**日期：** 2026-08-21  
**状态：** 视觉方向已由用户确认，待书面规格确认  
**范围：** 训练首页、统一动作库、训练准备、实时训练、训练总结、记录入口、计划入口和热量联动  
**视觉选择：** A「沉浸训练」为默认，不在本期实现左右双画面对照模式

## 1. 背景与问题

当前产品已经支持 17 个徒手动作、摄像头姿势识别、中文语音纠正、动作示范、单组总结和本地历史记录，但页面仍像功能验证工具，而不是用户愿意持续打开的健身产品。

主要问题：

1. 动作库和训练区是两套选择入口。动作库有 17 个动作，训练区却另列深蹲和开合跳两个按钮，形成明显冲突。
2. 摄像头、动作素材、骨架、指标和说明文字同时争抢主画面，用户不知道训练时应该看哪里。
3. 旧准备画面使用抽象人体或动作图片填充摄像头区域，容易出现人物被裁切、动作阶段没入画和“这是真人还是示范”的混淆。
4. 页面缺少稳定的产品层级：训练首页、动作库、计划、记录和实时训练没有明确分工。
5. 训练中需要抬头或离屏完成动作，语音必须成为第一反馈通道，画面只能辅助，不能依赖用户持续阅读。
6. 热量、节奏和响应时延虽然有产品价值，但当前没有清楚区分“训练核心信息”和“训练后分析信息”。

本设计把产品重组为一个相机优先、语音优先、素材分工明确的训练体验。

## 2. 设计目标

### 2.1 主要目标

- 用户打开产品后能在 10 秒内理解今天可以练什么、如何开始。
- 17 个动作只保留一个选择来源，不再出现动作库与训练按钮不一致。
- 开始训练后，用户自己的实时摄像头画面成为唯一主视觉。
- 准备页品牌图、动作标准素材和实时摄像头三类资产用途固定，不再混用。
- 训练中只突出次数和当前一条可执行纠正，其他数据退到第二层。
- 桌面和手机分别使用横版、竖版品牌图，禁止用同一张图强行裁切。
- 语音和视觉反馈继续遵守“新动作立即使旧信息失效”的实时规则。
- 计划、记录和热量使用同一批训练数据，形成训练前、训练中、训练后的闭环。

### 2.2 非目标

- 本期不实现 Peloton 式左右双画面课程。
- 本期不引入账号、云同步、付费体系或远程视频课程。
- 本期不把生成的品牌人物当成标准动作，也不用于姿势判定。
- 本期不宣称普通摄像头能够测量真实肌肉发力、关节受力或医学风险。
- 本期不重写已经验证通过的 17 个动作分析器和反馈调度器。

## 3. 核心原则

1. **相机优先。** 训练开始后只让用户自己的画面占据舞台中心。
2. **语音优先。** 用户不看屏幕也能知道当前最重要的纠正。
3. **一次一条。** 屏幕和语音同时只保留一条仍然有效的指导。
4. **素材有边界。** 品牌图负责情绪，动作素材负责教学，摄像头负责识别。
5. **完整优于铺满。** 动作示范和摄像头宁可留边，也不能裁掉头、手或脚。
6. **指标靠边。** 次数是训练中主指标；热量、节奏、时延是次指标或总结指标。
7. **不制造假精度。** 未设置体重时不显示虚构热量；低置信度时不输出姿势负评。

## 4. 信息架构

产品保留一个单页应用，不新增前端框架和路由依赖。顶层使用明确的视图状态：

```ts
type AppView = "home" | "library" | "training" | "plan" | "history" | "summary";
```

顶栏/侧栏只包含四个长期入口：

- 训练：进入首页，显示今日推荐和开始入口。
- 计划：显示预设计划、每周目标和完成进度。
- 记录：显示训练日历、历史列表和趋势摘要。
- 设置：管理体重、语音、骨架显示、隐私说明和摄像头偏好。

手机端使用底部导航；进入正在进行的训练后隐藏长期导航，避免遮住摄像头和误触。

### 4.1 单一动作选择来源

`EXERCISE_ORDER` 和 `EXERCISE_PROFILES` 继续作为 17 个动作的唯一数据源。删除硬编码的深蹲/开合跳双按钮选择器。所有入口——首页推荐、动作库、计划和“再练一组”——最终只调用同一个动作选择函数。

选择动作后进入训练准备状态，而不是跳到另一套动作按钮。

## 5. 页面和状态设计

### 5.1 训练首页 / 准备首页

首页使用已确认的深色雕塑人物品牌图：人物跪在训练包旁，处于准备训练的状态，一只眼睛有克制的白色微光，背景是暖光私人健身房。

品牌图的语义是“准备开始”，不是动作示范。

- 桌面使用横版 16:9 资产。
- 手机使用单独生成的竖版资产。
- 使用 `<picture>` 和媒体条件进行艺术方向切换，不依赖 `object-position` 猜裁切位置。
- 图上只覆盖今日推荐、计划时长、动作数量、估算热量范围和开始按钮。
- 未设置体重时，热量位置显示“设置体重后估算”。

首页下方只放三类内容：

1. 今日推荐计划。
2. 最近一次训练的继续入口。
3. 本周目标摘要。

完整 17 动作库通过“浏览全部动作”进入，首页不平铺全部动作。

### 5.2 动作库

动作库统一展示 17 个徒手动作，支持按下肢、上肢、核心和全身有氧筛选。

每张动作卡显示：

- 动作名称和训练类别。
- 主要肌群和辅助肌群。
- 已验证的缩略图或动画。
- 推荐视角、训练模式和估算强度。
- “开始训练”主操作。

动作媒体只能使用已核对的资源。素材标签与动作不一致时显示文字与安全占位，不使用相似但错误的图。

### 5.3 训练准备

用户选定动作后进入准备区：

- 显示动作名称、所需空间、推荐拍摄角度和三个关键动作要点。
- 标准动作素材使用固定比例容器和 `object-fit: contain`，完整展示所有阶段。
- 品牌图不再出现。
- 用户主动开启摄像头后，准备素材让位于真实视频。
- 摄像头权限、模型加载、入镜和校准分别显示独立状态，不用一个“请后退”文案覆盖所有错误。

### 5.4 实时训练：A 沉浸模式

训练开始后进入全幅相机舞台：

- `<video>` 与姿势画布占据主舞台，使用 `object-fit: contain` 保留摄像头完整画幅；剩余区域使用中性深色填充，不放大裁切视频。
- 桌面端右上只显示完成次数；目标次数、热量和当前节奏作为小型次指标。
- 左侧使用精简阶段轨道；手机端隐藏阶段轨道，避免遮挡身体。
- 标准动作是左下角可折叠参考窗，默认小尺寸；使用 `contain`，不得裁切。
- 底部是唯一的 Coach Ribbon：标签、当前纠正、语音播放状态。
- 骨架默认关闭。用户在设置中主动开启后才显示，且骨架不能改变识别结果。
- “暂停”“动作参考”“结束本组”放在舞台下方或安全边缘，不覆盖身体关键点。

Coach Ribbon 必须继续复用现有结构化 `CoachEvent` 和反馈优先级，不从中文文案反向解析状态。

### 5.5 单次结果

上一动作卡片不再长期占据镜头旁的大面积空间。完成一次动作时：

- 计数立即更新。
- Coach Ribbon 短暂显示“合格”或本次最重要问题。
- 详细问题、次要问题和下一次建议写入可展开的“上一动作”抽屉。
- 用户已经开始下一次动作时，上一动作的语音立即失效，但结构化结果仍保留在抽屉中。

### 5.6 训练总结

用户结束训练后立即停止摄像头和推理，再显示总结：

- 总次数/有效保持时间。
- 合格次数/合格率。
- 有效运动时间。
- 估算热量。
- 平均节奏。
- 教练响应时延，使用“跟手/正常/偏慢”解释，不要求普通用户理解 P95。
- 最常见问题和下一组唯一重点。
- “再练一组”“选择其他动作”“查看记录”三个操作。

总结页明确显示摄像头已关闭、画面未保存。

### 5.7 计划和记录

计划页首版只使用预设计划，不实现自动生成器：

- 全身均衡。
- 下肢与核心。
- 快速心肺。

计划由现有 17 个动作组成，记录动作、目标次数/时长、组数和休息时间。计划进度使用训练会话结果更新。

记录页复用现有本地历史数据，增加：

- 日历/周视图。
- 有效训练分钟。
- 估算热量。
- 合格率趋势。
- 最常见纠正问题。

所有数据仍只保存在当前设备。

## 6. 视觉系统

### 6.1 风格

方向是克制的运动编辑感，不是深色工程仪表盘，也不是健身房促销页面。

- 页面背景：暖灰白 `#F3F1EC`。
- 主文字：近黑 `#17191A`。
- 强调色：珊瑚橙 `#EF654B`，只用于主要动作和重要纠正。
- 成功色：克制青绿 `#147D73`。
- 卡片使用少量边框和留白，不大面积使用玻璃拟态。
- 中文使用系统优先的苹方/思源黑体；数字可使用简洁几何字体回退。
- 不使用 emoji 充当产品图标。

### 6.2 图片资产分工

| 资产 | 用途 | 禁止用途 |
| --- | --- | --- |
| 品牌横版/竖版 | 首页、准备品牌状态、营销展示 | 标准动作、摄像头替身、姿势判定 |
| 动作库媒体 | 动作卡、动作详情、可折叠参考窗 | 填满实时摄像头舞台 |
| 用户摄像头 | 入镜、校准、实时训练 | 保存、上传或作为历史缩略图 |
| 骨架画布 | 可选诊断/辅助理解 | 默认主视觉、动作示范 |

品牌资产落地文件：

- `public/assets/brand/ready-hero-desktop.png`
- `public/assets/brand/ready-hero-mobile.png`

源图来自本次用户确认的生成结果，最终复制进项目，不依赖临时目录和第三方热链。

## 7. 热量联动

热量只作为估算，使用：

```text
kcal = MET × 3.5 × 体重(kg) ÷ 200 × 有效运动分钟
```

规则：

- 体重由用户在设置中输入并仅保存在本地。
- 没有体重时不使用隐藏默认值，显示“设置体重后估算”。
- 只计算有效运动时间，不计算校准、暂停和长休息。
- 每个动作 profile 增加经审核的 MET 值或范围及来源说明。
- 训练前显示范围，训练中显示次要累计值，训练后显示本次估算值。
- 页面始终显示“估算”，不把结果包装成精确医学测量。

历史记录需要向后兼容：旧记录没有体重、有效运动时间或热量时显示 `—`，不得伪造补算。

## 8. 组件与代码边界

不引入框架，继续使用 TypeScript 和语义化 DOM。为避免 `main.ts` 继续膨胀，新增小型纯模块：

- `ui/view-state.ts`：顶层视图和训练视图切换。
- `ui/exercise-library.ts`：从 profiles 生成统一动作卡和筛选。
- `ui/training-stage.ts`：只负责相机舞台、指标和 Coach Ribbon 渲染。
- `ui/summary-view.ts`：只负责总结数据格式化与渲染。
- `calories.ts`：纯函数计算、范围估算和显示格式。
- `plans.ts`：首版预设计划数据。

`main.ts` 继续负责摄像头生命周期、Worker 通信、分析器选择和会话协调，不再直接组装所有页面结构。

分析数据流：

```text
摄像头帧 → Pose Worker → ExerciseAnalyzer → FrameAnalysis
                                      ↓
                               CoachFeedback
                                      ↓
                    TrainingStage + Voice + SessionSummary
                                      ↓
                   Calories + Local History + Plan Progress
```

## 9. 状态与异常处理

- 摄像头被拒绝：保留准备页，显示浏览器级解决办法，不进入训练态。
- 模型加载失败：允许重试，不让品牌图假装已经识别。
- 人体未检测：显示“未看到完整人体”，不直接说“后退”。
- 边缘裁切：只有低置信关键点自身接近边缘时才提示调整距离。
- 语音不可用：视觉纠正继续工作，明确显示“当前浏览器暂不支持语音”。
- 品牌图加载失败：显示同色系渐变和品牌文案，开始训练仍可用。
- 动作素材加载失败：显示动作名称、步骤和要点，不显示破图。
- 体重缺失：热量显示设置入口，不猜测。
- 页面切换：训练进行中离开训练页前弹出产品内确认；结束后关闭摄像头。

## 10. 无障碍与可用性

- 所有图标按钮有可读名称和不少于 44×44 像素的触控区域。
- 仅保留一个 `aria-live` 教练播报通道；语音合成接管时不重复让读屏朗读同一句。
- 训练状态变化不移动键盘焦点；训练结束后将焦点移到总结标题。
- 文本与背景满足 WCAG AA；纠正状态不能只靠颜色表达。
- 支持 `prefers-reduced-motion`。
- 手机训练态隐藏底部导航，Coach Ribbon 避开系统安全区。
- 正文手机字号不低于 16px；辅助标签可以更小，但不能承载关键动作信息。

## 11. 测试与验收

### 11.1 单元测试

- 17 个动作仍全部来自同一 profile 数据源。
- 动作筛选、选择和计划入口都更新同一个 `selectedExercise`。
- 热量公式、缺失体重、暂停时间排除和显示范围。
- 旧本地记录向新 schema 的兼容读取。
- 视图状态切换不误停或重复启动摄像头。
- Coach Ribbon 不显示过期事件，语音优先级回归继续通过。

### 11.2 浏览器测试

- 1440×900：首页横版完整、实时舞台不裁人、参考窗不遮挡身体。
- 390×844：使用竖版品牌图；无横向滚动；进入训练后隐藏底栏。
- 品牌横竖两张图片加载成功，没有第三方热链。
- 选择 17 个任一可训练动作都能进入同一训练准备和实时舞台。
- 开启/关闭摄像头、模型失败、语音不可用、人体丢失均有正确界面。
- 完成单次动作、完成整组、再练一组和进入记录的完整流程。
- 热量在未设置体重时不显示数值，设置后训练中和总结一致。

### 11.3 回归要求

- 现有动作分析、语音、反馈、存储和时延测试全部通过。
- TypeScript 类型检查和 Vite 生产构建通过。
- 浏览器控制台无错误和破图。
- 不改变“画面只在本机处理、不保存、不上传”的实现事实。

## 12. 实施顺序

1. 固化横竖品牌图片和视觉变量。
2. 建立顶层视图状态和统一导航。
3. 合并 17 动作选择入口，删除硬编码双按钮选择器。
4. 重构首页、动作库和训练准备页。
5. 将实时训练改为 A 沉浸舞台和 Coach Ribbon。
6. 加入热量纯函数、体重设置和记录兼容。
7. 接入计划、记录和总结页面。
8. 完成桌面、手机、无障碍和全流程回归测试。

## 13. 已确认决定

- 采用 A「沉浸训练」作为默认实时训练布局。
- 不采用普通居家健身真人作为品牌主视觉。
- 品牌人物参考用户提供图片：深色雕塑感、暖光健身房、跪姿准备、单眼微光。
- 桌面和手机分别生成横版、竖版，不进行破坏性裁切。
- 品牌图可以不是健身动作，但必须明确放在首页/准备语境中。
- 真正开始识别后，品牌图立即让位于用户自己的摄像头。
- 标准动作素材只作为动作教学和可展开参考，不填充实时画面。
